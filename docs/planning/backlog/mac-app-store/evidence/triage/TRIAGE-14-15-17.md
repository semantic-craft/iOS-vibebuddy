## 14 — OpenCode bundle 引用与认证输入：可行（已实测）

### 结论

商店版可以让 OpenCode **直接加载 .app bundle 内的插件**，不需要把 JS 复制到 `~/.config/opencode/plugins/`，也不需要第二个安装包或 bridge。插件能自行解析商店容器里的端口与 token。

### 证据 1：绝对路径插件可加载

`opencode.json` 的 `plugin` 数组接受绝对路径。opencode 将其规范化为 `file://` URL 并记录 `plugin_origins`：

```
"plugin": ["file:///…/FakeVibeBuddy.app/Contents/Resources/hooks/opencode/vibebuddy.js"],
"plugin_origins": [{ "spec": "file:///…", "source": "…/xdg/config/opencode", "scope": "global" }]
```

标记文件证明模块被求值且导出的工厂被调用：

```
module-evaluated 2026-09-08T04:19:48.953Z
factory-called dir=~/Projects/iOS-vibebuddy
```

复跑：
```
XDG_CONFIG_HOME=$S/xdg/config XDG_DATA_HOME=$S/xdg/data \
XDG_STATE_HOME=$S/xdg/state XDG_CACHE_HOME=$S/xdg/cache \
opencode debug config
```

### 证据 2：bundle 内插件可取得商店端口与 token

插件用 `import.meta.url` 定位自身，读取同目录 `endpoint.json`（bundle 内静态资源），再读商店容器的 `port` / `token`：

```
here=…/FakeVibeBuddy.app/Contents/Resources/hooks/opencode
resolved={"port":9880,"tokenLen":22,"source":"store-container"}
```

（tokenLen 为虚构 fixture 的长度，不是真实 token。）

### 拟定实现

- bundle 内保留单一 `vibebuddy.js`；解析顺序 env → 同目录 `endpoint.json` → 直接版默认值。直接版不带 `endpoint.json`，行为不变。
- 商店安装器只写 `opencode.json` 的 `plugin` 条目（一行路径），卸载时移除该条目。**没有任何可执行代码离开 bundle。**
- 未验证项：`opencode.json` 中他人已有 plugin 条目的合并与还原；商店 app 需要 `~/.config/opencode` 的目录授权（票 11 目前只列 Claude 与 Codex 两处，需扩列）。

## 14 — Codex 严格 argv marker：可行（已实测端到端）

### 结论

**不能加环境变量前缀；改为指向 bundle 内的同名脚本。** 未修改的直接版安装器照样识别该命令，双向接管与卸载都成立。

### 证据 1：未修改直接版的识别结果

直接调用 `hooks/install-codex-hooks.py` 的纯函数：

| 命令形状 | `is_forwarder` |
|---|---|
| `"/Applications/VibeBuddy.app/Contents/Resources/hooks/vibebuddy-forward.sh" codex` | **True** |
| `VIBEBUDDY_PORT=9880 "…/vibebuddy-forward.sh" codex` | False |
| `/usr/bin/env VIBEBUDDY_PORT=9880 "…/vibebuddy-forward.sh" codex` | False |
| 直接版仓库路径（对照） | True |

`is_approval`（bundle 内 `approval-hook.sh codex`）与 `is_capture`（bundle 内 `capture-terminal.sh`）同样为 True。

原因：`is_forwarder` 要求 `shlex.split` 后恰好 2 个 token、`basename(argv[0]) == "vibebuddy-forward.sh"`、`argv[1] == "codex"`。任何环境前缀都会变成第 3 个 token。

### 证据 2：真实隔离 Codex CLI 执行 bundle 路径 hook 并送达商店端口

`CODEX_HOME` 隔离，`hooks.json` 只含 bundle 路径命令（无 env 前缀），forwarder 为商店变体（同名、从容器读 `port`/`token`），监听器在 9881：

```
HIT path=/hook?agent=codex bytes=536 auth_present=True auth_len=29 event=SessionStart
HIT path=/hook?agent=codex bytes=613 auth_present=True auth_len=29 event=Stop
```

codex exec 退出码 0。（`--dangerously-bypass-hook-trust` 仅用于隔离探针跳过信任确认；产品路径仍需用户在新会话中重新信任。）

### 其它 CLI

只有 Codex 是严格 argv 匹配。Grok / Qwen / Kimi / Antigravity / Claude 全部按**子串**匹配（`"vibebuddy-forward.sh" in command` 等），bundle 路径与环境前缀都能识别。Claude 的 hook 甚至用独立 `args` 数组，不做 shell 解析。

## 15 — Codex Desktop 等待信号：**不存在**（实测否定）

### 结论

Codex 的 rollout 流**不持久化审批等待事件**。商店版在沙盒里又连不上 app-server socket（probe2 已证 EPERM）。因此票 15 描述的「Desktop 等待时手机收到 read-only card」在当前边界内**没有可用信号**，不能实现。

### 证据 1：642 个真实 rollout，零条等待事件

`~/.codex/sessions` 共 642 个 `.jsonl`（4.0 GB），其中 618 个含 `task_complete`（即真实完成过回合），`originator` 出现 2786 次 `"Codex Desktop"`。

| marker | 命中文件数 |
|---|---|
| `task_complete` | 618 |
| `session_meta` | 642 |
| `exec_approval_request` | **0** |
| `apply_patch_approval_request` | **0** |
| `request_user_input` | **0** |
| `elicitation_request` | **0** |

### 证据 2：持久化的 event_msg 类型清单里没有审批

抽样 40 个 rollout 的 `event_msg.payload.type` 全量分布：

```
agent_reasoning, token_count, agent_message, task_started, user_message,
patch_apply_end, task_complete, thread_settings_applied, sub_agent_activity,
web_search_end, mcp_tool_call_end, image_generation_end, context_compacted,
turn_aborted
```

顶层行类型：`session_meta` / `event_msg` / `response_item` / `world_state` / `turn_context` / `inter_agent_communication_metadata` / `compacted`。`world_state` 是会话配置快照（agents_md、permissions、skills…），不含等待状态。

### 证据 3：架构上审批是实时 RPC，不是日志条目

`CodexAppServerReducer.serverRequestMethod` 只认带 `id` 的 JSON-RPC **请求**；审批经由 app-server 的 serverRequest 通道下发并等待回应。rollout 是线程条目历史，天然不记录这种瞬时请求。`CodexRolloutMonitor` 里对 `exec_approval_request` 的分支对 rollout 路径而言是死代码。

### 证据 4：隔离 Codex 被沙盒拒绝的命令也没有产生审批事件

隔离 `CODEX_HOME` + `-s read-only` + `approval_policy=on-request` 运行一个写文件命令，结果是 `Operation not permitted`，rollout 只记录 `custom_tool_call` / `custom_tool_call_output`，无任何审批事件。exec 模式不升级审批。

### 附带观察

`approval_policy` 分布：`never` 7401 次、`on-request` 150 次。即便只看 on-request 的回合，也没有任何审批事件落盘。

### 待用户决定的选项（不擅自削减范围）

1. **保留 Desktop 观察、去掉等待提醒**：rollout 能可靠提供 `task_started` / `task_complete` / `turn_aborted` / `item_completed`，商店版可以显示 Desktop 任务的进行与完成，只是不提示「正在等你批准」。票 15 改为进度观察，等待提醒移出商店范围。
2. **整体推迟 15**：先交付 09–14、16–18，Desktop 等待作为后续版本议题。
3. **另找信号**：需要 Apple Events 或读取 Desktop 私有状态，两者都被沙盒与审核规则挡住，本轮不推荐。

无论选哪个，票 18 的审核材料都必须如实描述 Desktop 只有进度观察、没有审批。

## 17 — Keychain 与双向接管

### 17a Keychain：**不能继承，必须重输**（实测）

用虚构条目（service `com.vibebuddy.kcprobe`、account `fixture-not-a-secret`、值 `fixture-value-0001`）与两个同 team（LQAVR62TK2）签名的探针 app：`kcdirect.app` 未沙盒，`kcstore.app` 用 `tools/vibebuddy-store.entitlements` 签名（`codesign -d --entitlements` 实见 `app-sandbox`）。测试结束已删除该条目，`security find-generic-password` 确认不存在。真实 `com.vibebuddy.secrets` 全程未读未写。

| 操作 | 主体 | dataProtection | OSStatus | 含义 |
|---|---|---|---|---|
| write | direct（未沙盒） | false | 0 | 成功 |
| write | direct（未沙盒） | true | -34018 | errSecMissingEntitlement：未沙盒 Developer ID app 无法用 data-protection keychain |
| read | store（沙盒） | false | **-25293** | errSecAuthFailed（关闭 UI 时）；开启 UI 时进程**无限挂起**，无可见对话框 |
| read | store（沙盒） | true | -25300 | errSecItemNotFound（沙盒 app 只看到自己的 access group） |
| write | store（沙盒） | false | **-25299** | errSecDuplicateItem：看得到条目存在，却既读不了也改不了 |
| write | store（沙盒） | true | -34018 | Developer ID 签名的沙盒 app 无 application-identifier |

结论：
- 直接版的 key 存在 legacy keychain（`KeychainStore` 未设 `kSecUseDataProtectionKeychain`），沙盒商店版**读不到**，也**不能覆盖同名条目**。
- 商店版必须使用**不同的 service 名**（例如 `com.vibebuddy.store.secrets`），否则连自己写入都会撞 `errSecDuplicateItem`。
- 商店版 UI 必须引导用户**重新输入** API key，并说明原因。票 17 已允许该分支。
- 商店正式构建带 provisioning profile 后 data-protection keychain 应可用于商店自身存储；这一点需在票 17 实施时用正式签名复验，不能凭本地 Developer ID 结果断言。
- **实现约束**：任何 keychain 读取都必须先 `SecKeychainSetUserInteractionAllowed(false)` 或等价手段，否则商店 app 会像本次一样静默挂死。

### 17b 双向 Hook 接管：可行（marker 兼容）

- Codex：见 14 的证据 1，bundle 路径命令被未修改的直接版识别为「自己的」，因此 `without_vibebuddy` 会在 direct 重装时清掉商店条目，反之亦然。**不会产生重复 hook。**
- Claude：`has_marker` 是子串匹配（`vibebuddy-forward.sh` / `approval-hook.sh` / `capture-terminal.sh`），路径无关；`install()` 用 `owned == [expected]` 比较，路径不同即整组替换。接管干净。
- Grok / Qwen / Kimi / Antigravity：同为子串 marker。

### 17c Status line 跨容器还原：**已确认会误删用户配置**

`install-claude-hooks.py` 把用户原 statusLine 存在 `SUPPORT_DIR/statusline-original.json`（默认 `~/Library/Application Support/vibebuddy`，可用 `VIBEBUDDY_SUPPORT_DIR` 覆盖）。商店版写自己的容器，两边看不到对方的备份。

用两个 SUPPORT_DIR 实测纯函数：

```
[1] direct install_statusline -> True        # 原命令存进 direct 备份
[2] store  install_statusline -> False       # 已有 wrapper，不重复包装（无递归 wrapper）
[3] store  uninstall_statusline -> True      # 备份在对方容器 → statusLine 被整个删除
    RESULT: user's original status line DROPPED
[4] direct uninstall_statusline -> True      # 自己的备份在 → 正确还原 ~/bin/my-statusline.sh
```

结论与实现约束：
- 好消息：跨版本**不会递归包装**（[2]）。
- 坏消息：`uninstall_statusline` 在找不到备份时 `data.pop("statusLine")`（[3]）。商店版的原生实现**不得照搬这个兜底**：找不到备份时应保留现有 wrapper 并显示恢复入口，绝不删除。
- 商店安装时若发现 statusLine 已是**对方版本**的 wrapper，应显示「另一版本正在接管，请先在该版本卸载」，而不是接管一个自己无法还原的配置。
- 反向（用户先装商店、后用直接版卸载）无法从商店侧修复，属于直接版既有行为；票 18 的审核说明与用户文档需要提到。
