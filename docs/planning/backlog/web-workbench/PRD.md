# 跨项目 Web 工作台

日期：2026-10-01
阶段：方向与接入准备；尚未实现。

## 用户目标

把 VibeBuddy 与 Writing Infra、Anamra结合，形成 Web 应用：提供项目分类、项目工作看板、辅助助手、任务看板及 agent 分类；能够从 Mac mini、MacBook 和 iPhone 访问。

本次明确的是后续方向和先行铺垫。没有决定合并仓库、替换原生客户端、购买服务或部署公网服务。
用户已确认「Namura」指本机 `anamra`。进一步明确：Agent 结合已有信息进行任务分类；Writing Infra 根据任务进度安排 Agent 工作；Web 应用承载这一流程，Cloudflare Access 是用户倾向的访问方案。

## 已核实的基础

- VibeBuddy 已有 `AgentSession`、`Snapshot.sourceID`、HTTP `/snapshot` 与实时 `/ws`。会话状态、控制能力与来源由 Mac 提供，见 [GLOSSARY](../../../../GLOSSARY.md) 和 [ADR-0020](../../../adr/0020-autonomous-task-progress-desk.md)。
- 现有 `/ws` 只接受请求头 bearer，见 `VibeBuddyMac/Sources/VibeBuddyMacCore/VibeBuddyServer.swift` 的 `buildApplication()`；浏览器接入需单独设计认证，不能假定现有原生客户端连接代码可以直接复用。
- Writing Infra 是技能、参考文件与脚本仓库；论文工作发生在各论文项目中。其 README 指向 `docs/paper-canvas.md` 和 `docs/argument-state.md` 等项目产物；不是已经可调用的任务服务。证据：同级 `writing-infra/README.md`，2026-10-01 只读检查。
- 本机 `anamra/README.zh-CN.md` 描述了 Inbox、Today、Review、Planning 等本地工作流；本轮没有核实其内部 schema 或导出 API。

## 建议的产品与数据边界（待接入设计确认）

| 内容 | 建议的权威来源 | Web 工作台职责 |
|---|---|---|
| 项目分类与项目身份 | 工作台保存显式分类和跨源映射 | 按项目聚合，允许未分类，不根据目录名自动合并 |
| 人的工作项、计划与验收 | Anamra 为候选任务权威；写入接口待核实 | 展示目标、下一步、关联会话与验收状态 |
| 写作进展与论证状态 | 各论文项目的 Writing Infra 产物 | 展示来源、更新时间和原文入口；保留作者确认边界 |
| agent 运行、等待、结果和可执行操作 | 对应 Mac 的 VibeBuddy | 按 agent、项目和主机查看，操作回到真实控制通道 |

工作项与 Session 分开：一个工作项可关联多轮、多 agent、多主机会话；会话结束不等于工作项验收，已读不等于已验证，断线不等于完成。保持现有生命周期语义。

跨机项目映射应使用稳定 ID，目录仅作为某台主机上的位置；repository remote 可作匹配线索，但不能单独决定项目身份。会话引用包含来源主机与来源会话身份，不能用标题作主键。

agent 品牌、任务角色和当前控制能力分别呈现。是否支持继续、回答或停止，来自实际能力，不根据 agent 名称或看板分组推断。

## 信息到执行的闭环

本节记录用户目标与建议设计，不宣称三个项目已具备这些集成能力。

1. **收集上下文**：从 Anamra 已有信息、用户选定的项目资料和 Writing Infra 状态记录获取上下文，保存来源与更新时间。
2. **理解和分类**：Agent 识别所属项目、任务类型、关联资料、依赖及缺失信息。分类可纠正；用户修正不会被下一轮自动分类静默覆盖。分类不等于获得执行授权。
3. **按进度安排**：结合 Writing Infra 的论证状态、当前阻塞和依赖安排下一项工作，例如补找某个主张的原始来源、核对引注、整理论证缺口。Writing Infra 提供规则和进度语义；持久队列与派发由工作台服务实现，不把技能仓库当作常驻调度器。
4. **分派执行**：通过 VibeBuddy 已支持的控制通道，在有对应材料、权限且在线的主机上安排合适 agent；展示排队、执行、等待用户、失败及取消的真实结果。
5. **回收结果**：产物和证据关联回原工作项，更新可观察进度，再评估后续依赖。会话报告完成不能自动证明论证成立或作者验收。

建议首个验收样例：一条已有研究笔记 → 归入对应论文项目 → 从状态记录识别待补证据 → 安排一项检索或核查任务 → 展示真实 Session 与产物 → 区分任务结果和作者确认。

调度实现需明确：以哪个版本的进度触发、同一任务如何避免重复派发、用户如何改派或暂停、主机离线如何排队，以及结果写回的权威位置。浏览器关闭后已安排的工作仍应由服务端记录和管理，不能依赖页面定时器。

## 访问与部署方向

建议让 Web 页面与其服务端 API 同源，由服务端连接各 Mac 的 VibeBuddy；现阶段这是候选拓扑，不先引入新的常驻服务或数据库。

- Tailscale 可继续承担私有主机互联。Cloudflare Tunnel + Access 是优先评估的 Web 入口，两者不成为领域模型中的必填依赖。
- 浏览器身份、工作台操作权限、Mac 的配对 bearer 分层处理；Cloudflare 登录通过不能直接获得全部 agent 操作权。
- 现有 Mac bearer 留在可信服务端；不放入网页源码、浏览器持久存储或 WebSocket URL。浏览器会话、WebSocket 握手、Origin 检查与写操作防伪造需要一起验证。
- 原生客户端继续使用现有接口；只有新 Web 接口需求经验证后，才决定共享或新增协议。先核实 HTTPS/WSS 地址表达能力，不假定当前 host/port 配对已经支持域名入口。
- 连接状态与业务状态分开。展示来源主机、数据时间和离线状态；重连先恢复权威快照，不把缓存结果显示为当前实时状态。
- 若选 Mac mini 承载工作台，需验证它能否连接 MacBook；MacBook 休眠时，工作台只能展示带时间的旧状态，不能代执行该机任务。

Cloudflare 产品能力核查起点（实施前复核）：[Access](https://developers.cloudflare.com/cloudflare-one/setup/secure-private-apps/)、[WebSocket](https://developers.cloudflare.com/network/websockets/)。

## 第一条可验收的纵向流程

1. 在一个页面显示一个真实项目、一项工作及其关联的真实 agent Session。
2. 接入一个论文项目的实际状态产物，保留原始来源；没有状态时显示缺失，不合成进度百分比。
3. 在同一页区分两台 Mac 的来源，验证断线与重连，不重复计算同一来源会话。
4. 用浏览器登录读取状态；未登录不可读，过期登录可恢复，实时连接可重连。
5. 后续再接一种真实支持的控制操作，验证权限、过期请求及重复提交；不以页面按钮存在作为功能完成证据。

只读步骤是接入顺序，不是把最终产品限制为只读看板。辅助助手需完成信息理解、任务分类、进度驱动安排和执行反馈的闭环；自动执行范围和调度策略待设计。
