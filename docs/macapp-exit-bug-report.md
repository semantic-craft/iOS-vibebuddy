# Debug brief: SwiftUI menu-bar app cleanly exits when idle (no crash)

> Hand this whole document to another AI/engineer. It's self-contained. The reader can't run on my machine, so it ends with diagnostic commands the human can run and paste back.

## Symptom
A macOS **menu-bar (LSUIElement) SwiftUI app** (`VibeBuddyMacApp`, the resident daemon for a Claude Code monitor) **terminates on its own ~1–4 minutes after launch while idle**. Specifically:
- **Clean exit, NOT a crash** — no `.ips` crash report is generated (verified: latest crash report is hours old; none at exit time).
- **Correlates with idleness**: when I was actively building/curling against it (system busy, app receiving requests) it survived ~10 min; left truly idle it dies in ~1 min.
- Launched as the app via `open` → dies clean. Launched as the **raw binary** from a non-GUI shell → exits with **code 1, no stderr** (just one stdout line "Hummingbird server started"), but that may be a headless-session artifact.
- The user sees the menu-bar icon "just disappear."

## Environment
- macOS **Darwin 25.5.0 (macOS 26.x)**, Apple Silicon.
- **Swift 6**, SwiftUI app lifecycle, **Release** build, **ad-hoc signed** ("Sign to Run Locally"), project generated by **xcodegen**.
- `Info.plist`: **`LSUIElement = true`**.
- Embeds an in-process **Hummingbird** HTTP/WebSocket server on port 9876 run in a `Task.detached`.

## Already ruled out / tried (did NOT fix)
1. **`applicationShouldTerminateAfterLastWindowClosed` → false** — added; no effect. (Also: a borderless `NSPanel` "glance" is always on screen, so "last window closed" never really happens.)
2. **`ProcessInfo.disableSuddenTermination()` + `disableAutomaticTermination(_:)`** in `applicationDidFinishLaunching` — added; the app **still** idle-exits in ~1 min.
3. **No-scene / hidden-icon theory** — ruled out: `@AppStorage("showMenuBarIcon")` is `true`, `LSUIElement` is `true`, the `MenuBarExtra` should be inserted.
4. **Not a crash** — no crash report, no NSException, exit is clean.

## Telemetry that FAILED (important constraint)
- `log show --predicate 'process == "VibeBuddyMacApp"' --info --debug` returns **nothing** — not even Hummingbird logs (Hummingbird logs to stdout, not os_log). My own `os.Logger(subsystem: "com.vibebuddy.app", category: "lifecycle")` `.notice` calls in the lifecycle methods **do not appear** in `log show` either. So I have **no working telemetry** to see the exit path. (Why might this app's unified-log entries not show up under a `process ==` predicate on macOS 26?)

## Architecture / relevant code (current, with the failed fixes in place)
```swift
@main
struct VibeBuddyMenuBarApp: App {
    @NSApplicationDelegateAdaptor(AppDelegate.self) private var delegate
    @StateObject private var model = MenuBarModel()
    @AppStorage("showMenuBarIcon") private var showMenuBarIcon = true

    var body: some Scene {
        MenuBarExtra(isInserted: $showMenuBarIcon) {            // changed from plain MenuBarExtra to isInserted: for a "hide icon" feature
            MenuContent(model: model)
        } label: { MenuBarLabel(model: model) }
        .menuBarExtraStyle(.window)

        Window("vibebuddy", id: "dashboard") { DashboardView(model: model).frame(minWidth: 760, minHeight: 480) }
            .windowResizability(.contentMinSize)

        Settings { SettingsView(model: model) }
    }
}

final class AppDelegate: NSObject, NSApplicationDelegate {
    func applicationDidFinishLaunching(_ notification: Notification) {
        NSApp.setActivationPolicy(.accessory)
        ProcessInfo.processInfo.disableSuddenTermination()
        ProcessInfo.processInfo.disableAutomaticTermination("background daemon must stay alive")
        GlobalHotkey.install()                         // Carbon RegisterEventHotKey
    }
    func applicationShouldTerminateAfterLastWindowClosed(_ s: NSApplication) -> Bool { false }
    func applicationShouldTerminate(_ s: NSApplication) -> NSApplication.TerminateReply { .terminateNow }
    func applicationWillTerminate(_ n: Notification) { /* Logger.notice — never seen in log show */ }
}
```
Other relevant pieces:
- `MenuBarModel` (`@MainActor ObservableObject`): in `init`, starts the Hummingbird server via `Task.detached(priority: .utility) { try await server.buildApplication().runService() }`; starts a 2s polling `Task`; creates a **borderless `NSPanel` "glance"** on the next main-runloop tick (`DispatchQueue.main.async`).
- The glance `NSPanel`: `styleMask: [.borderless, .nonactivatingPanel]`, `level = CGShieldingWindowLevel()`, `isFloatingPanel = true`, `hidesOnDeactivate = false`, `collectionBehavior = [.canJoinAllSpaces, .fullScreenAuxiliary]`, `isReleasedWhenClosed = false`. Shown via `orderFrontRegardless()`.
- `AppActivationPolicy` toggles `.regular`/`.accessory` (reference-counted) when the dashboard/settings windows open/close.

## The questions for you
1. **Why would a macOS 26 LSUIElement SwiftUI `MenuBarExtra` app cleanly self-terminate (~1–4 min, idle, no crash) despite `disableSuddenTermination`/`disableAutomaticTermination`?** Candidate hypotheses to evaluate: `MenuBarExtra(isInserted:)` lifecycle quirk; the `Task.detached` Hummingbird/NIO `runService()` returning/cancelling and tearing down something; SwiftUI deciding there are no "active" scenes; an NIO/structured-concurrency precondition; macOS 26 new reaper behavior for accessory apps.
2. **Why does `log show --predicate 'process == "VibeBuddyMacApp"'` capture nothing**, and what's the right way to capture the exit on macOS 26 (predicate by `processImagePath`/`senderImagePath`? `log stream`? Console.app? an `atexit`/signal handler? running under `lldb`?).
3. Concrete next diagnostic + the actual fix (other than a LaunchAgent `KeepAlive` workaround).

## Diagnostic commands the human can run + paste back
```bash
# 1) Watch it die + timestamp (don't touch the app meanwhile):
open -a VibeBuddyMacApp; while pgrep -x VibeBuddyMacApp >/dev/null; do sleep 5; done; date

# 2) Live unified-log stream while it dies (try several predicates):
log stream --level debug --predicate 'senderImagePath CONTAINS "VibeBuddyMacApp" OR eventMessage CONTAINS "VibeBuddy"'
# in another terminal also try:
log stream --predicate 'process == "VibeBuddyMacApp"'

# 3) Who/what terminated it — system-wide around the exit time:
log show --last 10m --predicate 'eventMessage CONTAINS "VibeBuddyMacApp" OR composedMessage CONTAINS "VibeBuddy"' --info --debug

# 4) Run under lldb to catch the exit (gives the call stack at termination):
lldb -o run -o 'bt all' /Applications/VibeBuddyMacApp.app/Contents/MacOS/VibeBuddyMacApp
#   (then leave it idle until it exits; lldb prints why + the stack)

# 5) Confirm it's truly clean (no crash) and the exit code:
/Applications/VibeBuddyMacApp.app/Contents/MacOS/VibeBuddyMacApp; echo "exit=$?"
```
The `lldb` run (#4) is the most likely to reveal the actual termination path/stack.
